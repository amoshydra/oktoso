Show the model, show the steps

Today the dock tells you what was read and how many tokens it cost, but not which model answered or what the assistant actually did. This draft adds a model chip with a picker and an activity block in the grammar the chat already uses.

The proposed dock

The header gains one control, the model chip. Under the answer, the evidence line becomes a collapsible activity block in the same grammar as the chat’s AGENT ACTIVITY: a quiet uppercase header, a step count, and a chevron.

Model selection

The chip shows the model that will answer the next question in this thread. Clicking opens a short list of the models the configured endpoint reports. Selecting one changes this thread only; past answers keep the model that wrote them.

Rules

  • Per thread, not global. A quick question can use the small model; a diagnosis can switch to the 27B.
  • Frozen while running. The chip is disabled until the run ends; the answer used the model it started with.
  • Stored on the thread. Reopening the dock or reloading keeps the choice. New threads inherit the hub default.
  • Only configured models. The list comes from the assistant endpoint; no arbitrary ids or URLs.
  • Visible failure. If the chosen model is unloaded or missing, the turn says so and offers Retry; it does not silently fall back.

Be precise about “tool calls”. Today the assistant has exactly one model tool, propose_session_action. Reading the session, searching, and loading history are hub-side context steps, not model tool calls. The block labels them differently so “the assistant searched” never implies the model chose to.

Contracts and events

// thread-level default for the next run
AssistantThread { …, model?: string }

// change it without starting a run
PATCH /api/v1/assistant/threads/:id   { model: string | null }

// live steps (SSE), persisted on the turn for reload
AssistantEvent += { type: "step", step: {
  id, kind: "context" | "search" | "history" | "model" | "tool",
  label, detail?, status: "running" | "ok" | "error", at, durationMs?
} }
AssistantTurn { …, activity?: AssistantStep[] }

Steps are emitted as the hub assembles context, so the dock can show “Searching…” before the first token. The model and tool steps follow when they happen. On reload, the persisted list renders the same block.

States

  • Running: the header shows the current step in the activity line (“Searching…”), the count grows, the block is collapsed unless the reader opened it. Collapsed shows a 4px dot per step; expanded is the same 49px tile grid as the chat, and selecting a tile opens its detail inline. The model chip is disabled.
  • Read-only scopes: the activity still lists context/search/model. No tool step, no action card. The footer says Read-only · no writes.
  • Error: the failing step is marked with the danger color and its message; the block auto-expands once. The model chip re-enables.
  • Empty: no activity block before the first answer.
  • Mobile: the chip moves under the title if the header gets tight; the step rows wrap at the detail, never truncate the model name. 44 px targets for the chip and menu rows.

Decisions

  1. Per-thread model vs hub default only. The draft is per-thread with a config default. If you want one knob, the chip becomes a read-only label and the model moves to Settings.
  2. Collapsed by default? Yes, matching the chat: a dot texture, then the tile grid. Auto-expand only on failure or when a tool call fires, because that is the case where the reader needs the cause.
  3. Keep the evidence line? Keep the trust clause (turns, failures, session as-of) and move token counts into the activity. One line, no duplication.
  4. Real tool loop? This draft shows the current architecture honestly. If the assistant later gets search/read tools, they appear as tool steps with no UI change.
